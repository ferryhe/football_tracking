# Production Workflow Final Managed PR Plan

> **For agentic workers:** implementation must use the managed-pr-development workflow. Every PR starts from the latest clean main branch, uses a dedicated implementation agent, receives separate specification and code-quality reviews, passes focused and required validation, waits for remote GitHub feedback, and merges only after all valid feedback is resolved.

**Goal:** replace the current collection of parallel Baseline, Broadcast, Deliverable, AI, and History entry points with one sequential production workspace and one grouped production-history workspace, while preserving the existing backend contracts and production artifacts.

**Architecture:** the frontend owns a versioned production draft and derives the current user step from the draft plus authoritative backend run state. Existing APIs remain authoritative for inputs, asset groups, configurations, runs, broadcast review, recomputation, rendering, artifacts, and quality reports. Field calibration is edited in source-frame pixel coordinates through a React Konva overlay. Configuration confirmation creates a uniquely named, operator-locked configuration snapshot with a content digest and persisted workflow lineage. Because the current configuration API permits update, delete, and same-name overwrite, this is a detectable logical lock rather than a server-enforced immutable object.

**Primary stack:** React 19, TypeScript, Wouter, TanStack Query, React Konva, generated API client, FastAPI backend, existing broadcast workflow helpers, Playwright browser tests, frontend unit/component tests, and the existing Python verification suite.

## Product Decision

The application has two primary user-facing workspaces.

### 1. Production Workspace

The operator starts from the original video and moves down one step at a time. The top of the page shows only a lightweight current-step indicator such as:

> Step 2 of 5 · Field calibration

The five user-facing stages are:

1. Original video
2. Field calibration
3. Trial and tuning
4. Full tracking and review
5. Final product

The five stages are not five separate tabs or five independently clickable cards. Only the current step is expanded. Completed steps collapse to summaries and may be reopened. Future steps are hidden or disabled until their prerequisites are satisfied.

Internal workflow states may be more detailed than the five user-facing stages:

- source
- calibration
- trial
- config_confirmation
- full_tracking
- review
- recomputing
- trajectory_ready
- rendering
- ready
- failed
- cancelled

### 2. Production History

History is projected from backend AssetGroups for the same original video. It is not a flat list of run identifiers. A normal group is keyed in the client by input_video.path; the current slug-derived group_id is a display/URL alias and must not be assumed globally unique. The unbound group uses the fixed unbound-legacy key.

Each group provides:

- Original-video identity and metadata
- Current activity and latest status
- Trial attempts
- Confirmed configuration snapshots
- Full tracking runs
- Manual-review and recomputation operations
- Render operations
- Failed and cancelled attempts
- Final product versions

A run is a final broadcast product only when:

1. The authoritative broadcast state is ready.
2. A verified broadcast.mp4 artifact is available.

The existing Follow Cam heuristic must not be used to classify a broadcast product.

## User Workflow

1. Select the original video.
2. Inspect source metadata and preview frames.
3. Draw or edit the field polygon on the image.
4. Verify the same approved polygon on three distinct source frames.
5. Start a bounded trial run.
6. Inspect the result and adjust parameters.
7. Repeat the trial until the operator accepts the result.
8. Derive and operator-lock a uniquely named, digest-verified configuration snapshot.
9. Start full tracking from the locked configuration.
10. Review uncertain candidates only when the backend requires review.
11. Recompute the reviewed trajectory when required.
12. Render and validate the broadcast product.
13. Preview and download the product in the production workspace.
14. Reopen the complete lineage later from grouped production history.

## Authoritative Data and Invariants

### Original Video and Grouping

- Production history consumes backend AssetGroups but uses input_video.path as the normal client group key.
- The slug-derived AssetGroup group_id may be used as a URL/display alias only after collision detection.
- The UI must not group only by display filename or assume group_id is globally unique.
- Unbound legacy runs appear in an explicit Unarchived records group.
- A production draft binds the original video signature: path, size_bytes, and modified_at.
- If any source-signature field changes, calibration and all downstream state are invalidated with an operator-visible explanation.

### Calibration

- Approved polygon points are stored in source-frame pixel coordinates.
- Points must be finite and inside the source-frame boundary.
- A polygon requires at least three points and non-zero area.
- Display-to-source-to-display round trips must stay within one display pixel.
- The UI must not silently clamp invalid coordinates.
- Pointer dragging may be visibly constrained to the canvas boundary; typed or restored out-of-range coordinates must raise validation errors rather than being silently corrected.
- Changing the approved polygon invalidates all three frame confirmations.
- Changing the source video invalidates calibration and all downstream work.
- A frame may be confirmed only when its preview is loaded, a valid polygon is visible, and the confirmation records the frame identity plus polygon digest.
- AI, configuration, detection, and fallback suggestions are advisory seeds only.
- Suggestion source and confidence must be visible to the operator.

### Trial and Configuration

- Trial requests use the approved polygon and exclusions.
- Failed or cancelled trials cannot be accepted as the configuration basis.
- A completed trial is still advisory until required result artifacts and quality signals are readable and the operator explicitly accepts it.
- Retrying creates a new run record whose parent_run_id points to the preceding trial in the same production chain.
- Configuration confirmation derives a UUID-named persisted configuration snapshot and stores its SHA-256 in the draft.
- The configuration metadata.production_workflow record contains schema version, workflow ID, base configuration, accepted trial run ID, calibration digest, source signature, and confirmation time.
- The full broadcast run parent_run_id points to the accepted trial run; recompute and render operations continue to point to the full broadcast parent.
- The full run notes persist a machine-readable workflow ID and expected configuration SHA-256 so history can detect later configuration modification or deletion.
- The full run uses the confirmed snapshot; it cannot use mutable unconfirmed form state.
- The locked snapshot must not retain trial-only start_frame, max_frames, temporary output, or legacy render settings.
- Editing source, calibration, or tuning after confirmation requires explicit invalidation.

### Broadcast and Product

- Backend run and broadcast status remain authoritative.
- Before starting trial, full tracking, recompute, or render, the UI checks for the backend's single active run, displays the occupying task, and handles the server race/conflict response.
- Refreshing the page must not create a duplicate run.
- Refreshing an active run resumes monitoring; cancelling or failing a run never resumes the same computation and instead requires an explicit new retry run.
- Manual review appears only when the backend reports review work.
- A ready status without a verified broadcast.mp4 is a blocked delivery, not a product.
- AssetGroup/list-runs payloads intentionally omit artifacts for ready broadcasts. Product verification is lazy on group expansion/detail through the dedicated artifacts endpoint and cached by run_id plus broadcast.status_generation.
- Only verified artifact URLs are rendered as product downloads.
- Operation children remain linked to the correct parent run.

## Independent Review Resolution

An independent review agent inspected this plan against the current routes, API service, generated client, broadcast helpers, tests, and CI. The review concluded that the six-PR sequence was sound but required revision before execution. No reviewer edits were applied directly; the controller evaluated and incorporated the findings below.

Accepted Critical resolutions:

1. Replaced the unsupported claim of server-enforced immutable derived configurations with uniquely named, operator-locked, digest-verified configuration snapshots.
2. Added persistent trial-to-configuration-to-full-run lineage through parent_run_id, workflow metadata, and machine-readable full-run notes.

Accepted Important resolutions:

1. Drafts now bind path, size_bytes, and modified_at so same-path source replacement invalidates calibration.
2. AssetGroup group_id is no longer treated as globally unique; input_video.path is the normal client key.
3. Ready-product verification is lazy through the dedicated artifacts endpoint and cached by run_id plus status_generation, avoiding list-page N+1 requests.
4. Trial-only frame range and output settings are explicitly removed from full broadcast requests.
5. Playwright, accessibility, coverage, aggregate scripts, and initial CI integration belong to PR1; PR6 only finalizes cutover gates.
6. The backend single-active-run limitation is part of workspace behavior and automated tests.
7. Refresh recovery is distinguished from cancellation/failure retry; cancelled work is never described as resumable.
8. History cancellation targets the active broadcast operation and deletion respects child-first constraints.
9. Trial acceptance requires readable evidence and an explicit operator decision.
10. Start-new-production and unfinished-draft replacement behavior is specified.
11. Three-frame confirmation is bound to a valid visible polygon and its digest.
12. Legacy AI, Deliverable, and Highlight capabilities remain available through unlisted compatibility routes and contextual advanced actions for at least one release.

Review conclusion after these resolutions: **executable under the managed multi-PR workflow**, subject to isolating the existing unrelated pnpm-workspace.yaml modification before PR1.
